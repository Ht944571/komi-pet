## 1. 目标与验收标准

### G1 · 跨平台可直装

Windows / macOS / Linux 三平台各有一个安装包，双击（或 `dpkg -i`）即可安装运行。

**验收**：在**从未装过 Python / Node 的干净机器**上安装 → 桌宠出现、看板能打开。
三平台各自的安装包**产出自 CI**（不是本地手工打包）。

### G2 · 零环境配置

用户不需要预装任何运行时。

**验收**：安装后的进程树里**没有系统 Python、没有系统 Node**（运行时已内嵌）；
安装包体积在 Tauri 路线下 ≤ 20 MB、Electron 路线下 ≤ 150 MB。

### G3 · 用户自选接入哪些 Agent

用户能在一个界面里看到「哪些 agent 可用 / 已接入 / 能提供什么」，并逐项开关。

**验收**：
- 界面列出全部登记项及其**能力徽章**（可读日志 / 可探进程 / 有 hooks）与**验证状态**；
- 关掉某个 agent 后，桌宠不再按它佩戴配件、看板不再统计它（**当轮即生效**）；
- 未验证项明确标注，不假装可用。
- ✅ **本条已达成的部分**：登记册 + 看板面板 + **健康检查**（自动检测路径是否存在，
  面板显示「正常/不可用/未知」，T1）已实现。

### G4 · 查看各 Agent 用量

**验收**：看板能按 agent 维度展示 轮次 / 调用 / Token / 模型 / 项目 / 会话 / 趋势，
且支持跨 agent 对比。数据口径与源数据**逐 token 可对账**。

### G5 · 不破坏既有行为

重构过程中桌宠的交互与动效**观感不退化**。

**验收**：现有 13 个测试文件全绿；
表现层重写后需**新增**逐帧比对或人工观感验收清单（眨眼曲线、配件入退场、气泡跟随）。

**关键数字：平台相关 5,155 行 vs 跨平台 4,982 行。**

也就是说**非平台代码已经过半**。重写不是从零开始，而是"换掉一半、搬走另一半"。
当初为「杜绝同一几何写两处」而做的令牌化动效与纯几何 `compute_placement()`，
现在正是跨平台的迁移载体 —— 那两件事没白做。

### 3.2 目标形态（分层）

```
┌─ 表现层（每平台一份实现，消费下层令牌）────────────┐
│  pet-windows / pet-macos / pet-linux              │  ← 重写
│   · 透明 + 置顶 + 点击穿透 + 托盘                  │
│   · 消费 wb_motion 令牌、wb_accessories 几何       │
└───────────────────────────────────────────────────┘
┌─ 设计层（跨平台 · 纯数据）────────────────────────┐
│  wb_motion.py（动效令牌）  wb_accessories.py（几何）│  ← 直接复用
└───────────────────────────────────────────────────┘
┌─ 探针层（接口统一，探测原语按平台）───────────────┐
│  wb_agent_presence.py                             │  ← 接口不变，原语分平台
└───────────────────────────────────────────────────┘
┌─ 登记层（跨平台 · 纯声明）────────────────────────┐
│  wb_agent_registry.py + assets/_agents.json       │  ← 直接复用
└───────────────────────────────────────────────────┘
┌─ 数据层（跨平台 · 纯标准库）──────────────────────┐
│  wb_usage/：采集 → 数仓(SQLite) → 接口 → 前端      │  ← 直接复用
└───────────────────────────────────────────────────┘
```

**关键约束**：表现层**只消费**下三层，不得反向依赖。
`wb_motion.py` 保持「动效数字的唯一出处」这条红线，否则三平台观感会各自漂移。

## 5. 技术方案

### 5.1 跨平台打包与环境依赖

**现状**：要求用户自备 Python ≥ 3.8（零第三方包，仅 DSH 解压需 `zstandard`）。

**目标**：不要求任何预装运行时。

| 平台 | 安装包 | 自启机制 | 签名要求 |
|---|---|---|---|
| Windows | NSIS / MSI | **HKCU Run**（现有实现可直接复用） | 建议签（否则 SmartScreen 拦） |
| macOS | `.dmg` | LaunchAgent plist | **必须** Developer ID 签名 + 公证（$99/年） |
| Linux | `.AppImage` / `.deb` | XDG autostart `.desktop` | 不需要 |

**依赖收敛**（必须做的三件）：
1. **运行时内嵌** —— 走 Tauri/Electron 后，Python 不再出现在用户机器上。
2. **`zstandard` 问题消失** —— 数据层用 Rust 实现时改用 `zstd` crate；
   若保留 Python 后端，则把 `zstandard` 打进包（4 层降级已能容忍缺失）。
3. **定价数据** —— 若接 `ccusage`（§5.3），它在包内自带定价表；
   自研成本计算则需要一张可更新的模型价目表。

**UI 渲染差异**（Tauri 特有风险）：WebView2(Chromium) / WKWebView(WebKit) /
WebKitGTK 三套渲染引擎，CSS 需真机回归。

### 5.2 Agent 接入的可扩展设计

**已落地**：声明式登记册 + 能力声明 + 开关（§3.2 登记层）。

**剩余设计**（T1）：

```
三级状态来源（按可靠性降级，运行时自动选择最高可用层）
  L1 hooks    agent 主动回调          → 能拿"思考中/等审批"   需要装 hook
  L2 日志活动度 读会话日志的最近写入时间 → 能拿"忙碌/空闲"      不需配合  ← 待实现
  L3 进程/端口  判断"活着"            → 只能表达"在跑"         已实现
```

**关键限制（必须写进文档，别指望 L3 包打天下）**：
**L3 对 CLI 类 agent 基本无效** —— Claude Code / Codex / Kimi 都寄生在
`node.exe` / `python.exe` 上，靠进程名判「在跑」不可靠。
L3 能稳定识别的是**有独立 GUI 或独立服务**的（WorkBuddy / ZCode / DSH-web）。

各能力的现状与目标：

| Agent 类型 | L1 hooks | L2 日志活动度 | L3 进程/端口 |
|---|---|---|---|
| GUI 型（WorkBuddy / ZCode / Cursor） | 可做 | — | ✅ 已可用 |
| 服务型（DSH） | 插件（脆，版本钉死） | 可做 | ✅ 端口 |
| CLI 型（Codex / Claude Code / Kimi） | **最优路径** | **推荐先做这个** | ❌ 不可靠 |

**健康检查**（T1）：登记册的 `verified` 目前是**手填**。
应改为**自动检测**：路径是否存在、探针是否命中过、数据源能否读出至少一行。

### 5.3 用量信息的获取与展示

**获取：三层来源按可靠性降级**

| 层 | 来源 | 能回答 | 现状 |
|---|---|---|---|
| 订阅配额 | agent 官方 status-line / endpoint | **「我还剩多少」**（最贴近真问题） | ❌ 未做 |
| 本地用量 | 会话日志解析 | token / 模型 / 项目 / 会话 | ✅ 4 源，目标 18+ |
| 活跃状态 | hooks / 日志 / 进程 | 在跑 / 忙 / 需审批 | ⚠️ 只有 L3 |

**关于 `ccusage` 的定位修正（已实测，重要）**

实测 `npx ccusage@latest codex daily --json`（2026-09-25）：

| 项 | 结论 |
|---|---|
| 可用性 | ✅ 跑通，退出码 0 |
| 数值正确性 | ✅ **Codex 总量 11,342,672 tokens，与本项目独立解析器逐 token 吻合** |
| 输出结构 | `{ daily: [{date, inputTokens, outputTokens, cacheCreation/outputTokens, cacheReadTokens, reasoningOutputTokens, totalTokens, costUSD, models[]}], totals: {...} }` |
| 额外能力 | **自带 `costUSD` 定价**（我们没有定价库） |
| 粒度 | **按天** —— 而我们是**按每次调用** |
| 耗时 | 首次 62s（含拉包）、二次 **20s** |
| 依赖 | 需要 Node ≥ 20（用户机器上未必有） |

**结论：定位为「覆盖面补充」，不是「替代」。**
- 它补**广度**（18+ 源、日粒度足够）+ **成本维度**（成本 USD 我们没有）
- 我们保留**深度**（每次调用 / 每轮 / 每项目 / 每会话的细粒度）与**零依赖**
- 集成方式：**低频后台调用（≥5 分钟一次）+ 结果缓存**，
  20s 的耗时绝不能进 2 秒一轮的采集循环；用户没装 Node 时**自动跳过、不影响主链路**
- 字段映射：`prompt_tokens ← inputTokens + cacheReadTokens + cacheCreationTokens`、
  `completion_tokens ← outputTokens`、`completion_thinking_tokens ← reasoningOutputTokens`、
  `total_tokens ← totalTokens`（已验证 `input+output+cacheRead+cacheCreation == totalTokens`）

**展示：两种载体，职责要分清**

| 载体 | 职责 | 原则 |
|---|---|---|
| **桌宠** | **指示灯 + 开关** | 不给细节；只表达「谁在跑 / 谁在忙 / 谁需要我」；配件是天然载体 |
| **看板** | **仪表盘** | 明细、趋势、对比、导出 |

**要补的两件事**：
1. **数据时效的显式表达** —— 现在「读不到就保留旧值」（对），但用户不知道数据是旧的。
   应显示为「变暗 + 标注时效」，**不假装新鲜**。
2. **跨 agent 统一时间线** —— 用户切 agent 时丢的是「整体感」（设计见 `桌宠跨Agent体验设计.md`）。

### 5.4 表现层重写的技术选型

| 维度 | Tauri v2（推荐） | Electron |
|---|---|---|
| 体积 / 内存 | 5–15 MB / 30–80 MB | 80–150 MB / 100–200 MB |
| 透明 + 置顶 | 支持 | 成熟 |
| **点击穿透** | ⚠️ 无 per-region hit-test，需 Rust ~60fps 轮询光标切换 `setIgnoreCursorEvents` | `setIgnoreMouseEvents(true,{forward:true})` 成熟 |
| macOS 透明 | ⚠️ **有已知 issue，必须真机验证** | 成熟 |
| 后端语言 | **Rust**（正好承接扫进程/探端口/解压逻辑） | Node |
| 上架约束 | `macOSPrivateApi:true` → 永久失去 Mac App Store | 无此约束 |
| 实践证据 | `taoes/pets`（透明+忽略鼠标+置顶+托盘） | **Clawd on Desk**（三平台已发布） |

**决策：Tauri v2。** 理由是场景特性 —— 这是**常驻不关**的应用，
30–80 MB 与 100–200 MB 的差别对「桌宠」很关键；且 Rust 后端正好承接现有系统操作。

**决策前必须做的验证（T4 的第一件事）**：
在 macOS **真机**（或 CI 的 macOS runner）上验证三件事：
① 透明窗口在**打包后**（非 dev 模式）是否正常；② 点击穿透是否可用；③ 多显示器 DPI 是否正确。
**任一不达标 → 退回 Electron**，不要硬扛。

```
T3 数仓止血 ────┐（独立，但最紧急：库在长）
                │

                                                                              【关键路径】

关键路径：T4.0 → T4.1 → T4.2/3/4 → T5

```

**建议的开工顺序**：T3（止血，小）→ T1（把接入做扎实）→ T2（扩大覆盖面）
→ 然后才进 T4（大工程，且需先做 T4.0 验证）。

**理由**：T4 是唯一的重写，风险最高、周期最长；在它之前把数据层与接入层做扎实，
重写时才只需要关注「渲染与系统集成」，不必同时改业务逻辑。

## 8. 风险与决策点

| # | 风险 | 影响 | 应对 |
|---|---|---|---|
| R1 | **macOS 透明/穿透不达标**（Tauri 已知 issue） | T4 选型推翻 | T4.0 先验证；备选 Electron（体积换成熟度） |
| R2 | **动效观感在重写后退化** | 产品核心体验受损 | 抽象接口时保留令牌语义；新增观感验收清单；关键动效做逐帧比对 |
| R3 | **三平台渲染引擎不一致**（WebView2/WKWebView/WebKitGTK） | 布局/动效漂移 | 真机回归；避免依赖引擎特有能力 |
| R4 | 数仓继续膨胀 | 查询变慢、磁盘占用 | T3 优先做（已 2.57 GB 且未收敛） |
| R5 | macOS 签名证书未就绪 | 用户打不开（Gatekeeper 拦） | 提前确认开发者账号 |
| R6 | `ccusage` 版本/接口变动 | 补充源失效 | 适配器隔离 + 失败自动跳过，不影响主链路 |
| R7 | 自研解析器与 ccusage 口径分歧 | 同一 agent 两个数 | 以**逐 token 对账**为准（Codex 已吻合）；差异则记文档 |

**需要在开工前确认的决策点**：
1. **开源协议**：若引入 AGPL 代码（如抄 Clawd），全项目必须 AGPL-3.0 且传染全部原创代码。
   → 当前建议：**不抄代码，优先用 MIT 的 ccusage**。需最终拍板。
2. **macOS 开发者账号**是否已具备（影响 T5 能否交付签名包）。
3. **是否保留自研解析器**：建议保留（细粒度 + 零依赖），ccusage 只作补充。

## 10. GitHub 同类项目与可借鉴之处

> 完整调研见 [`跨平台与agent接入评估.md`](跨平台与agent接入评估.md) §3。此处只列**结论性**借鉴点。

| 项目 | 许可 | 借鉴什么 | 明确不借鉴什么 |
|---|---|---|---|
| **Clawd on Desk**<br>20+ agent、三平台 | **AGPL-3.0**（美术另计） | 三层接入模型、12 状态动画的状态机（多会话 + 优先级 + 最小显示时长）、主题脚手架、自定义 HTTP agent 注册 | **代码不能抄**（传染）；**美术素材不在 AGPL 内**。其接入层 100 文件 / 3.7MB，我们**不复制那个代价** |
| **ccusage**<br>18+ 源 | **MIT** | **可作为数据后端**（已实测）；`--json`、`--offline` 定价缓存、命名空间 CLI（`ccusage <source> daily`） | 不替代自研解析器（粒度更粗） |
| **Token Tracker** | MIT | **只记 token 计数、不记 prompt 内容** —— 直接对应我们的数仓膨胀与隐私问题（T3） | — |
| **Agent Usage Widget** | MIT | **订阅配额**追踪（比 token 计数更贴近真问题）；**「诚实状态」**：数据过期就变暗 + 标时效，不假装新鲜 | 它是原生 macOS 专属 |
| **AIUsage** | MIT | TS + `better-sqlite3` 架构（与我们最像）；桌面托盘 widget | 需 Node 20+ |
| **taoes/pets** | 见仓库 | **Tauri 2 透明 + 忽略鼠标 + 置顶 + 托盘** 的最小实现 —— T4 的选型参考 | 极简，无业务 |
| **VPet** | 见仓库 | 动画体系 + Mod/插件机制 + Core 可嵌入 | Windows WPF，不适合做跨平台基座 |
| **Star Office UI** | MIT | 空间化多 agent 表达（「每 agent 一个工位」） | — |
| **Clawmetry** | MIT | OpenTelemetry 标准；遥测可视化与告警 | — |
