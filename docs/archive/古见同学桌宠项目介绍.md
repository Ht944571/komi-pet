# 古见同学桌宠 · 项目介绍

## 项目是什么

这是一个把动漫角色「**古见硝子**」（《古见同学有交流障碍症》里那个说话有交流障碍、动不动就脸红的紫发女孩）做成 Windows 桌面宠物的项目——一只永远浮在桌面最上层、挂着深蓝椭圆想法泡泡的小可爱，会按时段打招呼，会看你的鼠标，会被戳一下先愣两秒再傲娇地回嘴。

她的原型来自一个真实存在的人设焦虑：动画里的古见"不敢和人对视、说话前先紧张地掏出笔记本"，于是**桌宠替她把说不出口的话全说了**——气泡里 70% 是自嘲、20% 是数据播报、10% 是傲娇警告，刚好对应原作里那种"想靠近但又怕打扰"的心理距离。立绘也分了两版：**Q 版**（大眼圆润、身高矮一截，互动时甩尾巴+捂脸）和**高冷版**（眼细长、表情克制，安静站着看你），右键菜单可切——等于你桌上养了两只性格相反的古见。

## 核心功能与亮点

桌宠层面：双击气泡自愈拉起看板、单击身体按 4 秒内连击次数分四档反馈（害羞 → 傲娇 → 嘟嘴 → 爆发喷水）、空闲时自己游动吐泡翻身换表情、悬停放大、光标跟随视线移动；看板层面：SQLite 读 WorkBuddy 本地用量库，按今天/7 天/30 天/全部四个时间窗口聚合展示总积分、Top 模型占比、每日消耗趋势。

但这个项目最值得拿出来说的不是"功能多"，是**立绘可换肤做到什么程度**——这是它和同类桌宠拉开差距的地方。

### 亮点一：双版本 × 6 表情 × 双朝向 = 24 张立绘可热切换
每张立绘都有正反两面 6 个状态：idle（默认平静）、happy（开心）、shy（害羞闭眼捂脸）、pout（嘟嘴）、blush（脸红）、stone（呆滞/石化的可爱版本）。换立绘不是"换张图就完事"——眼睛坐标、脸颊坐标、肤色、眼线色都得跟着标定，否则眼睑会画歪、腮红会贴到脖子上。

### 亮点二：像素级面部特征自动检测（`tools/detect_face.py`）
眼睛用虹膜特征色（古见的紫瞳约 `(62,48,73)` 像素值）做连通域检测——深色连通域检测行不通，因为古见的紫发和深色描边会跟眼睛连成一大片；腮红优先检测立绘自带的红晕（设面积 ≥ 2000px 阈值排除耳朵和阴影），无红晕时退而求其次在"眼外下方候选网格 + 皮肤覆盖率迭代收缩"找最佳位置；皮肤均色采样 → 眨眼盖板色。整套检测器让"换新立绘"从 1 小时手工标定降到 1 行命令。

### 亮点三：三段式拟真眨眼 + 高斯随机间隔
闭眼 99ms（ease-in 加速下落）→ 全闭保持 66ms → 睁眼 165ms（ease-out 减速抬起），眼睑用从立绘采样的肤色（不是深色——深色会把古见紫瞳盖得看不出"闭"），保持段画睫毛阴影线+重睑线（古见是大眼，双睑明显）。眨眼间隔从最初的均匀分布改成高斯 `gauss(5.5, 1.4)` 钳制 [2.5, 9.0]s，模拟真人"心血来潮"的不规律感。

### 亮点四：跨平台兼容骨架
虽然这个版本只跑 Windows，但核心层（路径解析、数据查询、卡片文案、位置记忆、状态上报、错误日志）抽到了 `wb_hover_core.py` 里，理论上 macOS 上换 Cocoa 实现就也能跑——项目早期就是 macOS Cocoa 悬浮球先跑通、再移植到 Windows 的。

## 开发中的实际问题与解决

**WNDPROC 回调被 GC 回收**。第一次跑起来窗口动两下就 0xc000001d 非法指令崩溃，延迟 60 多秒才暴露——根因是 WNDPROC 回调桩如果在类的方法里 `cast` 一份临时对象再注册到 `WNDCLASS.lpfnWndProc`，函数返回时 Python GC 立刻收掉那块内存，注册到 Windows 那边的是悬空指针；那块内存被复用覆盖后 Windows 派发消息就跳进垃圾代码。修法：模块级单例 `_WNDPROC_STUB = WNDPROC(_wndproc)`，整个进程就这一份；再补一句 `DefWindowProcW.argtypes = [HWND, UINT, WPARAM, LPARAM]`，64 位句柄才不会被 c_int 截断成访问违例。

**画面上下颠倒**。古见立绘第一次显示出来是倒着的。根因是 GDI+ 的 `DrawImage` 接受的是自上而下逻辑坐标，CreateDIBSection 的内存却是自下而上的 DIB，我"自作聪明"加了个 `_fy(y, h) = H - y - h` 翻转，结果翻反了。修了半天才明白应该把 `_fy` 改成恒等函数，让 GDI+ 自己处理坐标转换。

**拖动鼠标"瞬移不跟手"**。这个问题最难定位——我以为是事件路由或双缓冲的问题，折腾了一晚上。真相是 `api_healthy()` 在主消息循环里每 500ms 探测一次看板服务，碰上只 accept 不响应 HTTP 的端口就干等满 500ms，结果鼠标事件全堆到这一秒后集中处理。修法：把健康探测挪到后台 daemon 线程，主循环只读缓存值——拖动立刻丝滑。

**双击气泡死活开不了看板**。用了 220ms 短定时器"模拟双击"，但系统双击窗口是 500ms，慢双击被拆成两次单击。改成接 Windows 原生 `WM_LBUTTONDBLCLK` 消息后正常——白学一次"别自己造轮子"的教训。

**"切尺寸后桌宠全废"**这个 bug 最戏剧性：右键切到 2x 后，动态互动动画、点击身体反馈几乎全没了，只剩双击泡泡开看板还能用。根因是旧版 `_recreate_window` 是「新建 hwnd + 销毁旧 hwnd」，而 `SetTimer` 是挂在 hwnd 上的——旧窗口一死，三个定时器全没；新窗口又没重新挂。结果 `_react()` 改了状态但没人重绘，看上去"全废了"，唯独"双击泡泡"是 wndproc 内同步调用幸存下来。修法是切尺寸时只调 `SetWindowPos` 改尺寸、不销毁 hwnd——保住 hwnd = 保住定时器和消息路由。验证时特意做了个 `--legacy` 模式复现旧实现，直接挂死进程——铁证如山。

**CPU 23.1% → 1.8%**。15fps 每帧重采样大 PNG 立绘太贵。加「脏检测 + 预缩放缓存」：立绘一次性重采样到显示尺寸缓存在内存，后续只走 `AlphaBlend` 1:1 合成，CPU 直接腰斩。GDI+ 构造 `GpBitmap from HBITMAP` 还会丢 alpha 通道——立绘合成出来一片黑底，绕了半天改用 `msimg32.AlphaBlend` 走预乘 alpha 才解决。

**数据端的隐 bug**。「模型分布·积分占比」饼图不随时间切换联动——切到"7 天"再切回"今天"，饼图还是老数据。定位到 SQL 视图 `v_call` 没 `day` 列，得 JOIN `v_turn` 后用 `WHERE t.day = ?` 过滤，前端加 `renderModelChart()` 在切档时重拉重绘。

## 工具与技术栈

- **语言**：Python 3.13（纯标准库 + ctypes，零第三方 GUI 依赖；PIL 用于立绘处理）
- **窗口与渲染**：Win32 GDI + GDI+（`UpdateLayeredWindow + ULW_ALPHA` 分层窗口、`WS_EX_LAYERED` 透明命中、`msimg32.AlphaBlend` 预乘 alpha 合成）
- **系统层**：ctypes + WNDPROC 消息循环、Toolhelp32 进程快照、`HKCU\Run` 注册表自启、`winsound` 运行时合成 WAV 音效
- **数据端**：SQLite 只读访问 WorkBuddy 本地 db、`http.server` 看板 API、HTML + Chart.js 看板前端
- **动效系统**：独立 `wb_motion.py` 模块集中管理节奏/缓动/眨眼/情绪/降级
- **换肤工具**：`tools/detect_face.py`（像素级眼/颊/肤色检测）、`make_sprites_komi.py`（古见立绘去底裁切）、`test_komi_morph.py`（表情过渡测试）
- **测试**：`test_motion.py`（动效 14 项断言）、`test_scale_switch.py`（缩放回归 + `--legacy` 复现旧 bug）、`test_blink_smooth.py`（眨眼 36 项）
- **角色资源**：古见原图来自 `古见同学展示页/assets/`（16 张 Q 版 jpeg 源图），`make_sprites_komi.py` 处理后输出到 `scripts/assets/`

## 现状与展望

桌宠现在在桌面上运行（pid 14040，scale 1.0，事件日志里能看到情绪同步 `emotion: fail → neutral` 在真实环境生效），守望进程在后台盯着 WorkBuddy.exe，开机自启项已注册到注册表 Run 键。整套代码 19 个 Python 文件、4 份设计文档、3 个测试工具。

下一阶段想做但还没做的：眨眼间隔和情绪/行为的轻微联动（害羞时眨得更频繁、专注时不眨眼）、多人协作模式（不同 WorkBuddy 账户显示不同立绘）、节日主题皮肤切换（圣诞/新年时古见戴圣诞帽）。如果你喜欢这个项目可以看看 `古见同学展示页/index.html`，是我用 WorkBuddy 写的人物档案展示页——把古见原作的"社交焦虑"主题用留白和淡紫配色做了视觉化。
