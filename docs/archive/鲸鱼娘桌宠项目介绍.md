# 鲸鱼娘桌宠 · 项目介绍

## 项目是什么

这是一个挂着「用量看板」名头的 Windows 桌面宠物 + 个人数据可视化小工具，最初只是想随时看到自己 AI 工具的余额和当天花了多少 token，后来慢慢长成了一只傲娇的鲸鱼娘。

项目有两块主体：**数据端**是一套轻量级看板（SQLite + http.server + 静态 HTML + Chart.js），读 WorkBuddy 的本地 SQLite 数据库，按"今天/7 天/30 天/全部"四个时间段聚合展示总积分、消耗、Top 模型和每日趋势；**表现端**是一只始终浮在桌面最上层的鲸鱼娘桌宠，用纯 ctypes + GDI+ 画的，没有 PyQt/Tk 之类第三方依赖——所以可以跟 macOS 上的 Cocoa 悬浮球保持近乎一致的视觉与交互。桌宠挂着个深蓝椭圆想法泡泡随机冒台词（问候、傲娇、提醒、报数据），双击泡泡自愈拉起看板页，单击身体按连击次数分四档反馈（害羞 → 傲娇 → 嘟嘴 → 爆发喷水），空闲时会自己游动吐泡翻身换表情，鼠标靠近还会抬头看你一眼。

整套做下来的核心思路是「**用系统能给的、不用我加的**」：所有窗口绘制、事件路由、进程调度都直接调 Win32 API，唯一的"图形资产"是一张 Q 版立绘 PNG（之前是古见同学，换过几次），连粒子效果都用 GDI+ 的 ellipse 现画。零第三方 GUI 库带来的好处是部署极其干净——一个 Python 解释器 + 一份脚本就能跑，体积不到 10MB；代价是 Win32 的坑几乎踩了个遍，下文会讲到。

## 做了什么、解决了什么

最早想做个 macOS 风格的悬浮球，结果在 Windows 上 Cocoa 没法用，于是重新写了一套等效的 Windows 悬浮球。趁着换皮的机会，把整个交互从「圆球」升级成「**桌宠**」——参考了 GitHub 上一个叫 DeepSeek-Balance-Whale-Widget 的开源项目的气泡文案写法，把数据可视化、傲娇互动、桌宠生命力这些原本分散的需求整合进一个角色里。从那以后改了十几个大版本，依次补了：双击自愈拉起服务（点泡泡不响应时自动诊断端口拉看板 API）、模型分布模块时间联动（之前换了时间段不刷新数据，根因是 v_call 视图没 day 列、得 JOIN v_turn）、傲娇四档互动（按 4 秒内连击次数分档，搭配台词/粒子/音效）、空闲自主行为（游动 + 吐泡 + 翻身 + 换表情）、主动互动（光标跟随、打招呼）、视觉交互动效（呼吸/尾鳍/漂浮/眨眼/视线/按压压缩/拖拽倾斜），以及最近上线的「打开 WorkBuddy 时自动唤醒桌宠」守望进程。

## 开发中踩过的关键坑

**Windows 编程这一段最疼**。第一次跑起来，窗口动了两下就 0xc000001d 非法指令崩了，延迟 60 多秒才暴露——根因是 WNDPROC 回调的桩函数如果在类的方法里 `cast` 一份临时对象再注册，函数返回时 Python GC 立刻收掉那块内存，注册到 Windows 那边的是悬空指针，恰好那一块又被分配器复用覆盖。修法是模块级单例 `_WNDPROC_STUB = WNDPROC(_wndproc)`，整个进程生命周期就这一份。

第二个坑是 `DefWindowProcW` 没声明 argtypes，导致 64 位 HWND 被当成 32 位 c_int 截断，user32 内部访问违例。一开始我以为回调里不能调它（怕破坏调用约定），其实只要把 `argtypes=[HWND, UINT, WPARAM, LPARAM]` 标好就安全。

第三个坑更隐蔽：拖动桌宠时鼠标"瞬移不跟手"，根因是 `api_healthy()` 在主消息循环里每 500ms 探测一次，碰上个只 accept 不响应 HTTP 的端口就干等满 500ms，结果鼠标事件全堆到这一秒后集中处理。修法是把健康探测挪到后台 daemon 线程，主循环只读缓存值——拖动立刻丝滑了。

**GDI+ 这一段也踩了一堆**。最初画面是上下颠倒的，因为 GDI+ 的 `DrawImage` 接受的是"自上而下"逻辑坐标，CreateDIBSection 的内存却是自下而上的 DIB；我自己加了个 `_fy(y, h) = H - y - h` 翻转，结果翻反了。调了一晚上单测才发现应该把 `_fy` 改成恒等函数。GDI+ 还有个坑：从 HBITMAP 构造 `GpBitmap` 时 alpha 通道会丢，结果所有带 alpha 通道的 PNG 立绘合成出来都是黑底，绕了半天改用 `msimg32.AlphaBlend` 做 1:1 合成才解决。

**眨眼是单独开了个"视觉交互动效"提案**才彻底重做的。第一版是「220ms 短定时器截断双击窗口」——结果慢双击被拆成两次单击，气泡双击死活开不了看板。改成接 Windows 原生 `WM_LBUTTONDBLCLK` 消息后才正常；之后又把眨眼从「深色椭圆盖眼睛」升级到「**三段式拟真**」：闭眼 99ms（ease-in 加速下落）→ 全闭保持 66ms → 睁眼 165ms（ease-out 减速抬起），眼睑用从立绘采样的肤色（而不是深色——深色会把眼睛"涂黑"），保持段画睫毛阴影线和重睑线模拟双睑，最近又把眨眼的随机间隔从均匀分布改成高斯分布，更像真实生物的"心血来潮"。

最戏剧性的是「**缩放切换后桌宠全废**」这个 bug——切尺寸之后动态互动、点击反馈全没了，只剩双击泡泡开看板能跑。最后用对照实验复现了根因：旧的 `_recreate_window` 是「新建 hwnd + 销毁旧 hwnd」，而 `SetTimer` 挂的是 hwnd——旧窗口一死，三个定时器全没；新窗口又没重新挂。结果 `_react()` 改了状态但没人重绘，看上去"全废了"，唯独"双击泡泡"是 wndproc 内同步调用幸存下来。修法是切尺寸时只调 `SetWindowPos` 改尺寸、不销毁 hwnd——保住 hwnd = 保住定时器和消息路由。

性能优化那一段是"从 23.1% CPU 干到 1.8%"。原本常驻 15fps 每帧重采样大 PNG，罪魁是「无变化帧也照画不误」。修法是「脏检测 + 预缩放缓存」：立绘先一次性重采样到显示尺寸缓存在内存，后续 15fps 只走 `AlphaBlend` 1:1 合成，CPU 直接腰斩。

数据端最隐蔽的是「**模型分布不跟时间切换联动**」——用户切到"7 天"再切回"今天"，饼图还是老数据。最后定位到 SQL 视图 `v_call` 没 `day` 列、得 JOIN `v_turn` 后用 `WHERE t.day = ?` 过滤，前端加了个 `renderModelChart()` 在切档时重拉重绘。

## 技术栈

- **语言**：Python 3.13（标准库为主，零 GUI 第三方依赖；PIL 用于立绘处理）
- **窗口与渲染**：Win32 GDI + GDI+（`UpdateLayeredWindow + ULW_ALPHA` 分层窗口、`WS_EX_LAYERED` 透明命中、`msimg32.AlphaBlend` 合成、`GdiplusStartup` 初始化、`PolyDraw`/`ellipse` 粒子）
- **系统层**：ctypes + WNDPROC 消息循环、Toolhelp32 进程快照、`HKCU\Run` 注册表自启、`winsound` 运行时合成 WAV（`SND_MEMORY | SND_ASYNC`）
- **数据端**：SQLite（用量数据库，只读访问 WorkBuddy 本地 db）、`http.server`（看板 API）、HTML + Chart.js（看板前端饼图/趋势图/Top 列表）
- **动效系统**：独立模块 `wb_motion.py`，集中管理节奏常量、缓动函数、眨眼状态机、情绪状态、降级档位；主文件只引用
- **自动化**：PowerShell 计划任务 + 自定义守望进程 `wb_whale_watcher.py`（5 秒轮询 WorkBuddy.exe 是否在跑，在则拉起桌宠，崩溃自动救活）
- **测试**：`tools/test_motion.py`（动效/情绪/眨眼 14 项断言）、`tools/test_scale_switch.py`（缩放切换回归 + `--legacy` 复现修复前实现）、`tools/test_blink_smooth.py`（眨眼平滑 36 项）

## 现状

桌宠现在在桌面上（pid 14040，scale 1.0），守望进程在后台盯着 WorkBuddy.exe，开机自启项已注册到注册表 Run 键，每次开 WorkBuddy 她都会自动冒出来——你说"打开 WorkBuddy 时鲸鱼娘就会启动"，已经做到了。整套代码 19 个 Python 文件、4 个 Markdown 设计文档、2 个测试工具，可运行状态稳定。
