# 桌宠作为多 Agent 载体 · 设计方案与实施计划

> **定位说明（2026-09-24 补充）**：本文档解决「**桌宠作为切换器**」——
> 用户操作桌宠来聚焦 / 激活 / 接管某个 agent。
>
> 另有 `桌宠跨Agent体验设计.md` 解决「**用户自己切、桌宠跟随**」这条**主路径**
> （覆盖日常 90%，不需要用户改变任何习惯）。
>
> **两者的关系**：
> - **跟随模式是主路径**（`桌宠跨Agent体验设计.md` 的 P1）；本文档的手动切换
>   **降级为兜底**（那份文档的 P3）——用于跟随失效的场景（无窗口的 CLI agent、识别不到）。
> - 两份**共享**同一套身份与视觉层（常驻徽章 / 领结身份色 / 状态分层，本文档 §4）与
>   同一套交接机制（本文档 §5 的 L1/L2 分级）。**改这两块时两份文档都要看。**
> - 两份的**指标侧重不同**：本文档以「切换后回退率」为核心（衡量"切得对不对"），
>   跟随模式以「误跟随率」为核心（衡量"跟得准不准"）。

> 目标：让古见同学桌宠从「用量显示器」升级为「多 Agent 的接待员」——
> 承载多个 agent（不同厂商 / 不同用途），支持低摩擦切换，且切换过程不破坏体验。
>
> 本文档只做设计，不含实现。§9 给出分阶段落地路径，P0 是低风险起点。

---

## 0. 一句话方案

**桌宠只统一「呈现」与「切换」，不去统一 agent 的能力。**

具体拆成三件事：

1. **给每个 agent 发一张名片**（扩展已有的 `AgentSource` 寄存器，补运行态 / 外观 / 能力）；
2. **把"切换"拆成三层语义**（聚焦 / 激活 / 接管），绝大多数时候用户只做最轻的第一层；
3. **身份可见性优先于动效表现**（常驻徽章 + 领结配色，不依赖动画）。

## 1. 现状与差距

### 1.1 今天是什么

桌宠目前是**单向显示器**：读 `~/.workbuddy/projects/*/*.jsonl` 等数据源，把用量画在头顶
气泡里（`wb_whale_win.py` 的 `_bubble_lines()`）。它对 agent 的唯一认知是
`agents/` 寄存器里的 `key / label / has_credit`——**只有"数据从哪来"，没有"怎么操作它"**。

### 1.2 缺的是什么

要承载多 agent，需要补三样今天完全没有的东西：

| 缺口 | 说明 |
|---|---|
| **运行态** | 某个 agent 现在在不在跑？忙不忙？需不需要我介入？——今天只知道"历史消耗了多少" |
| **控制面** | 怎么把控制权交给它：唤起窗口 / 快捷键 / 注入上下文 |
| **聚焦状态** | "我现在是在跟谁说话"必须成为一个**被记住的、可见的**状态 |

### 1.3 可以复用的资产（这是本项目独有的优势）

| 资产 | 位置 | 复用于 |
|---|---|---|
| Agent 寄存器 | `wb_usage/agents/__init__.py`（`SOURCES` / `available_sources()`） | 名片的数据面，直接扩展 |
| 设计令牌单一出处 | `wb_motion.py`（12 小节，全部量化到 15fps 整数倍） | 切换动效时长/曲线直接从这里取 |
| 成熟的状态机动效 | OK 完成态：`OK_POP_IN_S=0.594`、`OK_POP_OUT_S=0.330`、`OK_GLYPH_MIN_SCALE=0.55` 过冲 | 徽章弹入/退场直接复用这套曲线 |
| 事件埋点 | `_report_event()` → `%TEMP%\wb-hover.events.log`（已记 `bubble_click` / `double_click` / `menu_*` / `drag_snap`） | §7 全部指标的数据源，**不用新建埋点体系** |
| 脱敏逻辑 | `wb_common` 的提问提取与脱敏（`extract_user_prompt`）+ 看板 `mask()` | 交接摘要（§5）必须复用 |
| 会话明细 | `ods_jsonl_event` / `v_turn` / `v_agent_*` | **交接摘要的数据已经躺在库里了**——别的桌宠做不到这点 |
| 画质降级 | `QUALITY_CHOICES`（完整/精简/关闭）+ `_auto_degrade()` | persona 的"动效档位"直接映射 |

> 关键结论：**这个方案不需要新数据链路**，需要的是在已有寄存器上加字段、在已有交互上加语义。

## 2. Agent 映射模型：一张「Agent 名片」

### 2.1 为什么是"名片"而不是"配置项"

如果每个 agent 的能力散落成各种 `if key == 'codex'`，代码会迅速腐烂。
统一成一张**声明式名片**（声明这个 agent 是什么、怎么探测、怎么唤起、长什么样），
新增 agent 仍然只动 `agents/` 一个目录——延续现有架构的隔离原则。

### 2.2 名片字段（在现有 `AgentSource` 上扩展）

| 分组 | 字段 | 现有? | 说明 |
|---|---|---|---|
| 身份 | `key` `label` | ✅ | 稳定标识 / 显示名 |
| 身份 | `vendor` `glyph` | ➕ | 厂商与徽章图形（身份可见性的载体） |
| 数据 | `has_credit` `root()` `parse_lines()` | ✅ | 用量链路，不动 |
| **运行态** | `runtime`: `probe()` / `busy_hint()` | ➕ | 进程名 / 窗口类 / 最近活动时间，判定 未安装·未运行·空闲·忙碌·需介入 |
| **控制面** | `activator`: `activate()` | ➕ | 唤起方式：激活窗口 / `cmd` / 深链（无则标记为"不支持激活"） |
| **外观** | `accent` `persona` | ➕ | 身份色 + 语气/动效覆盖（见 §6） |
| **能力** | `capabilities` | ➕ | `can_inject` / `can_resume` / `can_concurrent`——**决定切换策略，不做统一假设** |

### 2.3 数据面 / 控制面必须分开

```
        数据面（已有）                      控制面（新增）
   ┌──────────────────────┐        ┌──────────────────────┐
   │ 采集 → ODS → VIEW     │        │ runtime 探测 → 运行态 │
   │ v_agent / /api/agents │        │ activator → 唤起      │
   └──────────┬───────────┘        └──────────┬───────────┘
              └──────────┬────────────────────┘
                         ▼
                  Agent 名片（统一声明）
                         ▼
              桌宠（呈现 + 切换）/ 看板（明细）
```

分开的价值：**采集失败不该影响切换，切换失败也不该让用量数字归零**。
现有架构已经天然支持这点（`query_db` 的 `ok=False` 表示"保留上次值"），要保持。

### 2.4 能力分级（不要假设 agent 都一样）

`capabilities` 不是布尔开关堆，而是**降级阶梯**：

| 能力 | 有 | 没有时降级为 |
|---|---|---|
| `can_activate` | 一键唤起 | 提示"请手动打开 XX"（**明确告知**，不静默失败） |
| `can_inject` | 直接注入上下文 | 生成摘要到剪贴板（用户手动粘贴） |
| `can_resume` | 导入历史会话 | 只给摘要，不给"继续对话"的承诺 |
| `can_concurrent` | 可与其他 agent 并行 | 切换时提示"切走会中断当前任务" |

## 3. 切换交互：三层语义分离

### 3.1 三层语义（本方案最重要的一条）

| 层 | 动作 | 成本 | 频率 | 是否动上下文 |
|---|---|---|---|---|
| **L-A 聚焦** | 让桌宠"面向"某个 agent：气泡显示谁的用量、看板默认看谁、徽章换成谁 | 极低 | 高频（90%） | **不动** |
| **L-B 激活** | 把该 agent 的窗口/终端调到前台并准备好 | 低 | 中 | 不动 |
| **L-C 接管** | 把当前会话上下文交给另一个 agent 继续 | 高 | 低 | **动**（§5） |

**为什么必须分开**：把三者揉成一个"切换"按钮的产品，会产生一种糟糕的体验——
用户只是想看看另一个 agent 今天花了多少，却被弹出了一个待办会话迁移确认框。

### 3.2 交互载体与手势分工

现有手势（`_pet_mouse` / `context_menu`）已经排得很满，加功能前必须先看清冲突：

| 现有手势 | 现在的行为 | 冲突 |
|---|---|---|
| 单击身体 | 按命中区域切形态（`_body_region` → `_morph_by_region`：头/脸/身/裙摆） | ⚠️ **与"切换"直接冲突** |
| 双击身体 | 一次互动反应（`_react`） | 尚可 |
| 长按身体（≥500ms） | 憋气释放反馈（`_long_press_release`） | 尚可 |
| 单击气泡 | 数据态无动作 / OK 态计数 | 可用 |
| 双击气泡 | 打开看板 | 不动 |
| 右键 | 菜单（大小 / 画质 / 形态风格 / 气泡 / 音效 / 退出） | 扩展位 |

**建议的手势重分配**（这是一处必须明说的取舍，会打破肌肉记忆）：

| 手势 | 新行为 | 理由 |
|---|---|---|
| **单击身体** | **轮换聚焦 agent**（下一个） | 最高频动作给最自然的动作 |
| 单击**头部** | 切形态（保留最常用的一档） | 头部是最"像摸头"的区域，保留互动感 |
| 长按身体 | 打开 agent 面板（替代原来的憋气释放） | 憋气释放是纯装饰，性价比低 |
| **滚轮** | 快速遍历 agent | 零学习成本，天然适合"多选一" |
| 右键菜单顶层 | 加「当前：XX」+ agent 列表（含各自运行态） | 已有菜单，扩展成本低 |
| 全局热键 | 循环切换聚焦（可选，需 `RegisterHotKey`） | 桌宠被遮挡时仍可用 |

> 降级选项：把"单击轮换"做成**可配置**（设置里选"单击=切形态 / 切 agent"），
> 给老用户保留原有手感。默认推荐新语义。

### 3.3 防误触（桌宠贴在屏幕上，误触成本很高）

- **拖动阈值与切换分离**：现有 `_moved` 阈值是 3px；切换必须发生在 `_moved == False` 的纯点击上（现有逻辑已如此，保持）。
- **轮换的"停留确认"**：如果 agent 数 ≥ 3，单击轮换容易点过头。建议**单击后 400ms 内再点 = 继续轮换，否则视为确认**——但视觉要即时反映（徽章立刻变），避免"点了没反应"。
- **不做"拖拽到边缘分配给某 agent"**：过度设计，且与现有的四边吸附（`DRAG_EDGE=24`）冲突。

## 4. 切换的视觉与状态反馈

### 4.1 铁律：身份可见性不能依赖动画

**用户必须在不看动效、不看气泡的情况下，一眼知道当前是哪个 agent。**
只靠"表情不同"区分 agent 是失败的——没人记得住 5 套表情的含义。

具体方案（贴合古见同学的人设）：

| 载体 | 说明 |
|---|---|
| **领结颜色 = agent 身份色**（主） | 她的领结是天生合适的载体（现有配色 `C_TXT_HEAD = 0xFFB4364F` 领结红）。换领结 = 换装，比"变身成另一个人"克制得多，符合人设 |
| **徽章图形**（辅） | 气泡左上角贴一枚 vendor glyph，常驻不消失 |
| **气泡抬头** | 气泡第一行前缀 agent 短名（如 `[Codex] 正在对话 · …`）——最低成本兜底 |

三者叠加：颜色给"感觉"，徽章给"确认"，文字给"精确"。

### 4.2 切换动效：三段式 + 必须可打断

复用 OK 完成态那套曲线（`wb_motion.py` 已是令牌单一出处）：

| 段 | 内容 | 时长建议 |
|---|---|---|
| 1 退场 | 立绘轻微下沉 + 淡出（**不整只消失**，避免"换人"的割裂感） | ~0.20s（≈`STATE_EXIT_S`） |
| 2 换装 | 领结/徽章变色 + 一次短促的"翻页/盖章"过冲 | ~0.33s（≈`OK_POP_OUT_S`） |
| 3 进场 | 徽章按 `OK_GLYPH_MIN_SCALE=0.55 → 1.0` 的过冲弹入 + 气泡刷新 | ~0.26–0.59s |

**总时长建议 0.35–0.60s**，并且：

> ⚠️ **动效必须可打断（interruptible）**：连续切换时第二次点击不排队，
> 直接从当前进度插值到新目标。高频切换场景下，"排队播完动画"是最容易被骂的设计。

时长取舍：< 300ms 看不出身份变化；> 800ms 有仪式感但高频会烦。350–600ms 是甜点区。

### 4.3 状态语义分层（不同状态不能用同一套视觉）

| 状态 | 视觉强度 | 表现 |
|---|---|---|
| 聚焦中 | 恒常 | 身份色饱和 + 徽章实心 |
| 已安装未运行 | 恒常 | 徽章描边、色偏冷 |
| 运行中但未聚焦 | 低 | 徽章实心小尺寸 |
| **忙碌（正在跑任务）** | **中（脉冲）** | 气泡呼吸脉冲 / 立绘轻微晃动 |
| **需用户介入（报错、等待确认）** | **高（唯一允许打断的级别）** | 跳动一下 + 音效 + 气泡转红 |
| 未安装 | 静默 | 徽章灰化；点击给出明确原因，不静默失败 |
| 无数据（如 Codex 无积分口径） | 不适用 | 复用现有口径自适应（积分显示「—」+ 说明） |

**原则：只有"需介入"允许主动吸引注意力。** 忙碌只是脉冲，不该弹提示、不该发声、
更不该**自动切换聚焦**——见 §8 的"自动 vs 手动"取舍。

### 4.4 多 agent 并发时的聚合表达

桌宠只有一只，但有 3 个 agent 在跑。**绝不能在同一只桌宠上挂多个气泡**（设计灾难）。

- 徽章改为**堆叠态**（小圆点 fan-out）
- 气泡显示聚合：「**N 个任务运行中**」
- 分布细节交给看板（`/api/agents` → `v_agent`）与右键面板
- 并发下"需介入"的 agent 优先提级显示（抢占徽章位）

## 5. 上下文 / 会话迁移

### 5.1 诚实的前提：没有通用方案

不同厂商的会话格式、状态存储、恢复机制完全不同。**追求"统一上下文协议"是幻觉**，
投入产出比极差。正确做法是**能力分级的阶梯式降级**：

| 级别 | 方案 | 依赖能力 | 成本 | 建议 |
|---|---|---|---|---|
| **L0** | 不迁移（纯聚焦切换） | — | 0 | **默认，覆盖绝大多数场景** |
| **L1** | **交接摘要（Handoff Brief）** | 剪贴板即可 | 低 | ★ **主力方案** |
| **L2** | 上下文文件注入（写 `handoff.md` 到工作目录，让目标 agent 读） | 目标能读文件 | 中 | 对 CLI 类 agent 首选 |
| **L3** | 原生会话导入（`--resume` / 导入历史） | agent 自身支持 | 高、易碎 | 按需，逐 agent 适配 |
| **L4** | 双向会话同步（共享会话存储） | — | 极高 | **明确不做** |

### 5.2 L1 交接摘要：数据已经现成

这是本项目最大的独有优势——**别的桌宠做不到，因为它没有数仓**。

**素材来源**（全部已有）：

| 素材 | 来源 |
|---|---|
| 最近 N 轮的用户提问原文 | `ods_jsonl_event.user_prompt`（已过 `extract_user_prompt`） |
| 轮次边界与时间 | `v_turn`（`turn_id` / `first_time` / `api_calls`） |
| 涉及项目 / 工作目录 | `v_turn.project_final` / `cwd` |
| 使用了哪些模型 | `v_turn.models` |

**摘要结构建议**（结构化 > 自由文本，便于目标 agent 解析）：

```
## 交接摘要（来自 <源 agent> · <时间>）
- 工作目录：<cwd>
- 任务：<最近一轮用户提问（脱敏、截断）>
- 已完成：<最近 N 轮的要点/标题>
- 未决：<最后一轮是否有未完成迹象>
- 用量：<N 轮 · X 积分 · Y token>
```

**三条硬约束**：

1. **必须脱敏**：复用 `wb_common` 的提取/脱敏与看板的 `mask()`（邮箱、手机号、绝对路径、长密钥）；
2. **默认需用户确认**再注入——摘要可能含敏感内容，自动外发到另一个厂商的 agent 是隐私事故；
3. **注入方式按能力降级**：`can_inject` → 直接注入；否则 → 复制到剪贴板 + 明确提示"已复制，去 XX 里粘贴"。

**记住用户的选择**（如"这个 agent 以后直接注入，不再问"），但**首次与敏感内容永远要问**。

### 5.3 为什么不做 L4

- 会话格式是各厂商私有且会变，维护成本无上限；
- 双向同步会产生**冲突与重复计费**（同一轮被两个 agent 各跑一次）；
- 一致性无法保证，出问题时用户无法归因。
- 结论：**L1+L2 覆盖 90% 需求且可控**，把省下的力气投到"身份可见性"和"切换时延"上，
  体验收益高一个量级。

## 6. 桌宠个性化表现的适配

### 6.1 主张：不换人格，换装束

这是人设层面的核心判断。两个选项：

| 方案 | 优点 | 缺点 |
|---|---|---|
| 每个 agent 换一套人格/立绘 | 区分度最高 | 破坏"古见同学"人设一致性；美术成本 ×N；用户记不住 N 套表情 |
| **只换装束与状态**（推荐） | 人设稳定；成本低；识别靠徽章更可靠 | 区分度依赖徽章设计质量 |

**推荐后者**：古见同学始终是古见同学——她是**接待员**，不是变身者。
不同 agent 的差异体现在：**身份色 + 徽章 + 语气档位 + 姿态（面向谁）**。

保留一个**克制的越界空间**：`persona` 可以覆盖外观与语气，但**不能覆盖核心行为红线**
（例如不能把她变成话唠——"古见几乎不说话"是产品红线）。

### 6.2 实现方式：persona 是"令牌覆盖层"，不是硬编码

现有架构的 `wb_motion.py` 已经是全部时长/幅度/颜色的单一事实来源，
persona 就应该做成它上面的一层覆盖：

```
wb_motion.py（默认令牌，全局唯一出处）
      ▲
      └── agents/<key>/persona.json（按 agent 覆盖）
              · accent       身份色（领结/徽章）
              · glyph        徽章图形
              · tones        语气文案（欢迎/忙碌/完成/失败）
              · motion       动效档位（映射到已有 QUALITY_CHOICES）
              · idle         待机行为开关
```

**严禁**在业务代码里写 `if agent == "codex": color = ...`。新增 agent = 加一个 json。

### 6.3 可配置项清单（建议先做前三项）

| 项 | 作用 | 优先级 |
|---|---|---|
| `accent` 身份色 | 领结/徽章配色 | ★★★ |
| `glyph` 徽章 | 身份图形 | ★★★ |
| `tones` 语气档位 | 4 种场景文案（给古见"跟不同 agent 协作"的口吻微调） | ★★ |
| `motion` 动效档位 | 严谨型 agent 可以更克制 | ★★ |
| `idle` 待机行为 | 是否参与自主玩耍 | ★ |
| 完整主题包（立绘替换） | 重度个性化，成本高 | ☆ 暂缓 |

## 7. 评估指标

### 7.1 北极星指标

> **切换后回退率（Switch-back Rate）**：切到某 agent 后 X 秒内又切回上一个的比例。
> **它同时反映"切错"和"切过去发现不对"**，是唯一能同时衡量交互成本与信息可见性的指标。

**当前基线未知，必须先把基线测出来**（P1 就要开始埋点），否则后面所有优化都是自我感觉良好。

### 7.2 指标分层

| 层 | 指标 | 定义 | 目标 | 埋点 |
|---|---|---|---|---|
| **效率** | 聚焦切换时延 | 触发 → 身份可见（P50/P95） | P95 < 150ms | `switch_begin`/`switch_shown` 时间戳差 |
| | 切换步数 | 到目标 agent 的操作数 | ≤ 2 | 事件计数 |
| | 激活成功率 | 唤起外部 agent 成功比例 | > 95% | `activate_result ok/fail` |
| **认知** | **切换后回退率** | 见上 | < 8%（先测基线） | `switch_focus` 时间序列分析 |
| | 身份误判率 | 代理指标：短时间内**重复提问**、对同一问题跨 agent 重试 | 下降趋势 | `v_turn` 中同 prompt 跨 agent 重复 |
| | 面板打开率 | 不确定当前是谁 → 去查（越低越好） | 下降趋势 | `menu_open` / 新增 `panel_open` |
| **打扰** | 误触率 | 无意图的切换（切换后立刻回退且间隔 < 1s） | < 2% | 时间序列 |
| | 打断率 | "需介入"提示被忽略的比例 | 观察 | `alert_shown` vs `alert_acted` |
| **迁移**（仅 L1+） | 摘要采纳率 / 编辑率 | 直接使用 vs 用户改过 | 采纳上升、编辑下降 | `handoff_accept` / `handoff_edit` |
| | 迁移后首轮追问率 | 迁移完还要补问 = 摘要没说清 | 下降 | 目标 agent 新会话首轮 prompt 是否像"补充说明" |
| **技术** | 探测开销 | CPU / 内存增量 | 无感 | 现有 `quality` 降级机制 |
| | 切换动效掉帧 | 是否守住 15fps 基准 | 不劣化 | 帧计数 |

### 7.3 采集方式：复用现有埋点，不新建体系

`_report_event()` 已经在往 `%TEMP%\wb-hover.events.log` 写事件，
新增事件（`switch_focus` / `switch_back` / `activate_result` / `handoff_*` / `alert_*`）
沿用同一套。分析时把 events.log 与数仓的 `v_turn` 按时间对齐，就能算出"回退率"与
"误判率"这类跨源指标。

> 注意：现有 `_report_event` 是**追加写入的纯文本日志**，用于长期分析需要
> 加一个轻量的日切/轮转，避免无限增长（可参考数仓那个 P0 膨胀教训）。

## 8. 设计取舍（必须明说的矛盾）

| # | 取舍 | 选项 A | 选项 B | 建议 | 理由 |
|---|---|---|---|---|---|
| 1 | 人格一致性 vs 区分度 | 每 agent 换人格 | 只换装束 + 强徽章 | **B** | 人设不崩、成本低；识别可靠性靠徽章而非记忆 |
| 2 | 动效仪式感 vs 高频切换 | 长动效（有仪式） | 瞬时（利落） | **350–600ms + 可打断** | 排队播动画是高频场景的体验杀手 |
| 3 | 自动迁移 vs 用户确认 | 全自动（爽） | 每次确认（噪音） | **默认确认 + 记住选择** | 摘要含提问原文，自动外发到别家 agent 是隐私事故 |
| 4 | 通用协议 vs 分级降级 | 追求统一上下文协议 | L0–L4 能力分级 | **分级** | 通用协议是幻觉；分级能诚实告知"这个不支持" |
| 5 | 桌宠承载 vs 看板承载 | 全塞桌宠 | 桌宠只做指示+开关 | **桌宠=指示灯+开关，看板=仪表盘** | 桌宠会遮挡屏幕，信息密度上限很低 |
| 6 | **自动切换聚焦 vs 手动** | 检测到某 agent 开始工作就自动切过去 | 永不自动切 | **永不自动切** | 用户会失去"我在跟谁说话"的控制感；只在"需介入"时提示 |
| 7 | 常驻探测 vs 开销 | 高频轮询（准） | 事件/低频 | 现有 1s tick + **重探测放后台线程** | 已有血泪教训：消息循环里做探测会卡拖动 |
| 8 | 单击语义变更 vs 肌肉记忆 | 直接改（更合理） | 保持旧语义 | **改，但可配置** | 新语义价值高，但给老用户留回退开关 |

## 9. 分阶段实施计划

规模标记：S（小，一个模块内）/ M（中，跨 2–3 个模块）/ L（大，含交互与美术）。
**每阶段都可独立交付并验证，不要求一次做完。**

### P0 · 地基：Agent 名片与聚焦状态（S）

| 项 | 内容 |
|---|---|
| 范围 | 扩展 `agents/base.py` 的 `AgentSource`：加 `vendor` / `glyph` / `accent` / `runtime` / `capabilities`（默认值保持向后兼容，现有源零改动）；新增聚焦状态持久化（写进已有的 `.whale_settings.json`） |
| 交付物 | CLI 能列出每个 agent 的 身份 / 可用性 / 能力；聚焦状态可读写 |
| 验收 | 现有 7 项桌宠测试 + 看板测试**全绿不回归**；新增 registry 单测 |
| 风险 | 低。纯数据层，不碰 UI |

### P1 · 聚焦切换（M）★ 最高价值

| 项 | 内容 |
|---|---|
| 范围 | 交互：右键菜单加 agent 分组 + 单击轮换（+ 头部保留形态切换）；视觉：常驻徽章 + 领结身份色 + 三段式可打断动效；气泡与看板跟随聚焦 |
| 交付物 | 能切、一眼看出切了；埋点 `switch_focus` / `switch_back` |
| 验收 | 切换时延 P95 < 150ms；动效可被下一次点击打断；**基线数据（回退率）开始积累** |
| 风险 | ⚠️ 单击语义变更打破肌肉记忆 → 提供可配置开关 + 首次启动一次性提示 |

### P2 · 运行态与并发表达（M）

| 项 | 内容 |
|---|---|
| 范围 | 后台线程探测各 agent 运行/忙碌（**严禁放消息循环**）；忙碌脉冲；并发聚合徽章 + 「N 个任务运行中」；"需介入"提级视觉 |
| 交付物 | 桌宠成为"状态指示灯"；埋点 `alert_shown` / `alert_acted` |
| 验收 | 探测开销无感（不劣化现有画质档位）；拖动不卡（回归验证） |
| 风险 | 探测多进程的 CPU 开销 → 复用现有 `_health_loop` 的后台线程模式与 `QUALITY_CHOICES` 降级 |

### P3 · 激活与热键（M）

| 项 | 内容 |
|---|---|
| 范围 | `activator` 实现（激活窗口 / 启动命令 / 深链）；全局热键循环切换（`RegisterHotKey`）；无激活能力的 agent 给出明确提示 |
| 交付物 | 一键唤起；埋点 `activate_result` |
| 验收 | 激活成功率 > 95%；不支持激活的场景不静默失败 |
| 风险 | 全局热键可能与其他软件冲突 → 可配置 + 冲突检测 |

### P4 · 交接（L1 / L2）（L）

| 项 | 内容 |
|---|---|
| 范围 | 交接摘要生成器（复用 `ods_jsonl_event` + `v_turn` + 脱敏）；确认 UI；注入方式按 `can_inject` 降级（直接注入 / 写 `handoff.md` / 复制剪贴板） |
| 交付物 | 能把会话上下文交给另一个 agent；埋点 `handoff_accept` / `handoff_edit` |
| 验收 | 摘要必过脱敏；首次与敏感内容强制确认；采纳率/编辑率可测 |
| 风险 | ⚠️ 隐私（必须确认）+ 各 agent 注入方式差异大（按能力降级，不做统一承诺） |

### P5 · persona 覆盖与个性化（M）

| 项 | 内容 |
|---|---|
| 范围 | `agents/<key>/persona.json` 覆盖层（accent / glyph / tones / motion / idle）；映射到现有 `QUALITY_CHOICES`；UI 里可调 |
| 交付物 | 不同 agent 有不同的"接待风格"，但人设一致 |
| 验收 | 新增 agent 只需加一个 json，不改业务代码 |
| 风险 | 低。但要守住红线：persona **不能**覆盖核心行为（古见几乎不说话） |

### 依赖关系

```
P0 ──┬─→ P1 ──→ P2 ──→ P3
     │           └─────────→ P4
     └─→ P5（可与 P2/P3 并行）
```

P0 是一切的前提；P1 是价值拐点；P2/P3 强化"状态可见"与"零摩擦"；
P4 是可选的高阶能力；P5 是收尾的个性化。

## 10. 风险与回滚

| 风险 | 缓解 |
|---|---|
| 单击语义变更引起困惑 | 可配置开关 + 首次提示；**保留旧语义作为默认的备选** |
| 多 agent 探测拖慢桌宠 | 重探测放后台 daemon 线程（现有 `_health_loop` 模式）；`QUALITY_CHOICES` 自动降级 |
| 徽章/身份色在多 agent 下不够区分 | 颜色 + 图形 + 文字前缀**三者叠加**，不只靠颜色（色盲友好） |
| 交接摘要泄露敏感信息 | 复用脱敏 + 默认确认 + 记住选择但敏感内容永远问 |
| 事件日志无限增长 | 参考数仓 P0 教训，加日切/轮转 |
| 新功能破坏既有功能 | 每阶段跑全量回归（现成 7 项桌宠测试 + 看板前端测试） |

**回滚策略**：每个阶段的功能都用 `wb_motion.py` 里的 `*_ON` 总开关模式
（现有 `OK_AUTODISMISS_ON` / `LINKED_CLOSE_ON` 就是这个模式），
出问题置 `False` 即回退到上一版行为，无需改代码。
