## 二、桌宠侧

### 2.1 七段动作状态机（`wb_anim.PetPhase`）

```
idle(坐着·循环) ──空闲 3 分钟──► doze(变困) ──► sleepy(困了·循环)
     ▲                                                │
     │                                         来任务  │
     └──────────────── wake(醒来) ◄───────────────────┘
                          │
                          └─► pickup(拿本子) ──► write(写字·循环)
                                                       │
                              idle ◄── present(举本子展示) ◄── 任务完成
```

| 动作 | 素材 | 播法 | 什么时候 |
|---|---|---|---|
| `idle` | `anim/idle/` 107 帧 | **循环整段** | 常态（没有任务在跑） |
| `doze` | `anim/doze/` 107 帧 | 一次性 | 空闲超 `MOTION.IDLE_DOZE_AFTER_S`（默认 180s） |
| `sleepy` | `anim/sleepy/` 107 帧 | **循环整段** | 变困播完 |
| `wake` | **复用 `doze` 倒放** | 一次性 | 睡着时来任务 |
| `pickup` | `anim/pickup/` 107 帧 | 一次性 | 坐着/醒来 + 来任务 |
| `write` | `anim/write/` 97 帧 | **循环写字段** | 任务进行中 |
| `present` | 复用 `write` 后段 | 一次性 | 任务完成 |

**两个复用设计**（都省了一半素材，且比重新生成更准）：

- **`wake` = `doze` 倒放**：观感就是「从托腮变回端坐」，首尾帧天然对齐
- **`present` = `write` 后段**：同一段视频里翻页之后的镜头

**触发判据与气泡 OK 态同源**（`_sync_bubble_mode` 里的「运行中会话数」）——
两者必须是同一个 n，否则会出现「气泡说完成了、她还在写」这种自相矛盾。

### 2.2 动作音效

五段素材里**四段自带音轨**（坐着 / 困了 / 拿本子 / 写字），**变困那段是静音轨**。

- **统一峰值到 60%**。原始峰值差 5.7 倍：`pickup` 95%（会刺耳）、`idle` 16.7%（几乎听不见）
- **循环播**的三种：`idle` / `sleepy` / `write` —— 都是持续状态，播一遍就没声了
- 变困**不硬塞音效**（素材没有就是没有）
- 右键菜单「**音效**」是**总开关**（互动音效 + 动作音效都归它管）
- ⚠️ **winsound 一次只能播一个** → 点击的互动音效会打断动作音效，
  所以 `_play()` 记了个 `_sfx_resume_at = now + 0.6`，0.6s 后自动接回来

### 2.3 24fps 不抽帧 + 内存优化

用户要求「**流畅优先，帧数不要减少**」，于是：

- 素材从 12fps 抽帧（54 帧/段）**重转为 24fps 原帧率**（107 帧/段，共 **525 帧**）
- **关键**：`_build_draw_cache` 建完预缩放缓存后**立刻释放原始位图**（`_anim_imgs`）

| | 优化前（12fps/259帧） | 现在（24fps/525帧） |
|---|---|---|
| 桌宠内存 | 205MB | **132MB** |
| 打包 zip | 51.6MB | **76.4MB** |

原始位图每帧约 950KB、预缩放后约 350KB，525 帧下差约 **300MB**。
**不做这步，24fps 会直接顶到 500MB+**；做了之后 132MB，比 12fps 时还小。

### 2.4 右键菜单卡顿

`TrackPopupMenu` 是**模态**的 —— 它自己跑消息循环，而**定时器照跳**，
`_anim_tick` 每 41ms 就把整个分层窗口重合成一遍，**跟菜单抢 UI 线程**。

**修**：`context_menu` 里 `TrackPopupMenu` 前后挂一个 `_menu_open` 闸门，
`_anim_tick` / `tick` 开头直接 return。实测**菜单开着时 20 次定时器 → 0 次重绘**。

### 3.2 时间维度：从「只有三个接口跟随」到「全部跟随」

这是今天耗时最多、也最有教训的一块。**改了三轮才对**：

**第一轮**：以为 KPI/日趋势/模型分布会跟随就够了 —— 但 `projects` / `clients` / `tops`
三个接口**压根没有 `days` 参数**，一直吃全量，旁边卡片在变、它们不动。

**第二轮**：给三个接口加了 `days` —— 但**漏了缓存 key**。
它们外面套着 `_cached(key, fn)`，key 原来是 `f"projects:{agent}"`，
**不带 days** → 切到近 7 天会命中「全部」那份缓存 → **数据看着还是不动，而且不报错**。

**第三轮**（用户反馈"切昨天/本月/上月/自定义数据完全不变"）：
真凶是 **`_daily` 自己又解析了一遍 days**：

```python
if days in ("today", "all", ""):  ...           # 走 WHERE 过滤，OK
else: n = max(int(days), 1); ... LIMIT n        # 'yesterday' → ValueError！
```

→ `/api/daily?days=yesterday` **返回 502** → 前端 `Promise.all` **整体 reject**
→ **后面所有 render 一个都不执行** → 整个看板停止刷新，**页面上一点报错都没有**。

**最终修法**：

1. **后端 `_day_cond()` 是时间口径的唯一实现**。`_daily` 改成**只有纯数字才走 LIMIT**，
   其余全靠 WHERE 过滤 —— 不再两处分叉
2. **前端 `loadAll` 每个请求各自兜底**（`safe()` 包一层 `.catch` 返回 null），
   单个接口挂掉不再拖垮整张看板
3. `/api/agents` 加 `days`：`dws_agent` 是全量物化表滤不了天 → 另写 `agents_range` 按区间现算
   （否则多 Agent 对比图**标题写「今天」、柱子是全量**）。agent 筛选按钮组**仍用全量**，
   不然切区间时按钮会跟着消失
4. KPI 卡片前缀改用 `rangeText()`（原来 `'近'+range+'天'` 会拼出「**近yesterday天积分**」）

### 4.3 转帧的两个连环坑（改素材必读）

**坑 1：删旧帧失败会静默中断转帧。**
`video_to_pet_frames.py` 写新帧前会 `os.remove` 旧帧，而这个删除被 safe-delete 拦下
（中文路径）→ 抛异常 → **整段转帧中断**。
最阴的是：前面的「帧画布 / 抽到 107 帧 / 统一内容框」日志**全都正常打印**，
只有最后那行 `✅ 107 帧 → 目录` 不出现 —— **看起来完全像成功**。
→ 已修（删除包 try/except），**但排查习惯更重要：转完直接核对 meta 的 count/fps**。

**坑 2：桌宠持有 PNG 句柄 → 覆盖写被拒。**
`PermissionError: [Errno 13]` —— GDI+ 加载后锁文件。
→ **转帧前必须先 `taskkill` 桌宠**（守望不用停，但转帧慢的话也停掉）。

### 4.4 「自测脚本自己制造假象」

排查菜单交互时绕了好几轮，全是自测脚本的问题：

- 验证「点击能否打开下拉」时，我先手动 `openRangeSel(true)` 再 `click()`
  —— 第二次点击是**正常的 toggle 关闭**，看起来就像"点了打不开"
- 两个 `setTimeout` 并行把顺序搞反（一个点「自定义」、一个点触发器）

→ **验证交互时只做那一个动作，别预先改状态**；**自测脚本要写成链式时序。**

### 4.5 `stopPropagation` 漏了会自伤

下拉里点「自定义」→ 事件冒泡到 `document` 的"点外部关闭" → **刚展开的日历被立刻收掉**。
→ 列表和日历的 click 都要 `e.stopPropagation()`。

### 4.6 头大小对齐：读下巴要留足够条带高度

`HEAD_SCALE` 的 1.27 是**并排条带 + 肉眼读**出来的，但**第一次用 30% 高的条带**，
**把写字的「脖子/衣领」当成了下巴** → 得出「待机头更大」的**反向结论**，白调一轮
（先缩到 0.80、又缩到 0.72）。
→ 改用 **45% 条带**才看清真相：**待机的头小，要放大 1.27**。

**另一个教训**：在这套素材上**自动测头大小不可靠**（道具、刘海、表情都干扰）——
宽度剖面被头发中分的凹陷骗、颜色找脸被刘海切成碎片、找下巴被本子带偏。
**并排条带 + 肉眼反而是最稳的**，不该在自动测量上耗那么多轮。

### 4.7 改前端前先确认 `api()` 的返回约定

我在修 `loadAll` 时写了 `kpi.data` / `agents.data` —— 但 `api()` 内部**已经 `return j.data`**，
全是 undefined → 每个 `if` 都不成立 → **等于所有卡片又都不刷新**。

### 4.8 SQL 的 `FILTER` 在 `WHERE` 之后生效

`_kpi` 里 `today_credit` 用 `FILTER (WHERE day=today)`。主查询一旦带 `days` 条件
（如近 7 天），**今天的行早被 WHERE 滤掉了**，FILTER 恒为 0
→ 表现是切到「昨天」后副标题写「今日 0.00」。
→ 修：今日值**单独再查一次**（只受 agent 约束）。

**修这个时又踩了自己的坑**：补查用了 `_conds()` 返回的 `rest` 去拼条件，
而 **`rest` 是「全部条件」、里面含 day_cond** → 变成
`WHERE day=today AND day='2026-09-27'` → 恒为空集。
→ 要用**纯 agent 条件**。

### 4.9 沙箱环境（会反复遇到）

### 4.10 多图共用锚点

万一误判（如 agent 跑超长本地任务 15 分钟无调用），气泡只是提前回落，下一笔事件自愈，无永久影响。

## 十一、补丁 5（00:20-00:45）：菜单弹不出修复 —— owner-draw 三个 Win32 常量连环坑

美术上线后用户报障：**右键菜单完全弹不出**。连环三个根因，全部是 **Win32 常量/协议手抄错**，
mock 测试与离屏渲染都测不到（只有真实 Win32 调用才触发）：

| # | 错误 | 后果 |
|---|---|---|
| 1 | `MF_OWNERDRAW` 手抄成 `0xB0`（真值 **`0x100`**） | 系统把 itemData(下标 1) 当字符串指针解引用 → `access violation reading 0x1`，构建中断 → 菜单弹不出 |
| 2 | `TPM_NONOTIFY` 挂在 `TrackPopupMenu` 上 | 它**连 owner-draw 协议消息一起拦**（不只命令通知）→ measure/draw 到不了 owner。修复 = 移除（`TPM_RETURNCMD` 本就不发命令通知，无副作用） |
| 3 | `WM_MEASUREITEM`/`WM_DRAWITEM` 手抄成 `0x0211`/`0x021B` | **那是 `WM_ENTERMENULOOP`/`WM_EXITMENULOOP`**（lparam 恒 0 → cast 炸 `NULL pointer access`）！真值 **`0x002C`/`0x002B`**。消息号错 → measure 全落 DefWindowProc → 菜单缩成 19px 默认尺寸 |

**破案路径（复用价值高）**：
1. err.log 铁证：`AppendMenuW access violation reading 0x1` → 常量错；
2. 修 #1 后菜单弹出但 **19×204px**（系统对未 measure 条目的最小尺寸）→ 查 NONOTIFY；
3. 修 #2 后 measure 到了但 `lparam=0`（`_menu_diag` 日志抓到现场）→ **最小 repro**
   （`tools/_repro_menu.py`：普通窗口跑同款菜单，60 行）→ repro 同样 lparam=0，且 stderr 抛
   `DefWindowProcW argument 4 OverflowError`（裸调用 64 位 lparam 溢出；桌宠本体已正确声明
   argtypes 无此问题）→ 顺藤查出 0x0211/0x021B 根本不是 measure/draw；
4. 修 #3 后真机验证：菜单 **291×416px**（272 内容宽生效），`PrintWindow` 渲染出完整看板美术
   （`_menu_printwindow.png`）。⚠️ **BitBlt 拷屏截菜单是透明的**——菜单窗口走 DWM 合成层，
   屏幕 DC 拷贝拿不到它，是截屏假象不是显示 bug；验证菜单视觉要用 `PrintWindow(PW_RENDERFULLCONTENT)`。

**防回归**：`test_menu_toggles.py` [G8] 把全部涉事常量（MF_*、WM_MEASUREITEM/DRAWITEM）对
SDK 真值锁死（现 22 项 PASS）；`_on_measure_item/_on_draw_item` 带一次性 `_menu_diag` 诊断；
`tools/_repro_menu.py` 留作菜单协议最小复现工具。全量回归 14 文件 PASS。

**教训**：手抄 Win32 常量=高危操作；mock 单测验证不了真实协议层——**常量字面量断言 +
真实 Win32 冒烟（或最小 repro）才是这类 bug 的防线**。

## 十五、补丁 9：菜单「字体重叠」根治 —— 弃 owner-draw，改自绘分层窗口（MenuSession）

**用户反馈**：右键菜单的字与下层内容**叠在一起**（此前还经历过"菜单弹不出"的连环修复）。
根因：**Win11 系统菜单窗口的背景合成不可控**——`MIM_BACKGROUND` 铺底在 DWM 合成时不可靠，
未绘制区域透出下层窗口；hover 切换的擦除时机也管不到。继续在 `TrackPopupMenu` 黑盒里补
背景/擦除是打地鼠。

**方案**：整个菜单改为**自绘分层窗口**（与桌宠本体同款 `UpdateLayeredWindow` 技术）：
背景天然不透明（逐像素 alpha）、每帧全量重绘（无残影）、美术自由度更高（真圆角+阴影）。

| 件 | 说明 |
|---|---|
| `MenuSession`（模块级类） | 布局/命中/绘制/消息循环一体。`run(owner_hwnd, pt)` 模态弹菜单，返回选中 cmd / 0（对齐 `TPM_RETURNCMD` 语义） |
| `menu_layout(items, m)` / `menu_hit(rows, y)` | 纯函数（[H] 单测锁死） |
| 绘制 | 全 GDI+（`Surface.round_rect` 新增 + 既有 text/ellipse/poly），配色仍走 `menu_item_style`（看板规范不变） |
| 子菜单 | 独立 `WBMenuClass` 分层窗口，**WS_EX_NOACTIVATE**（鼠标仍由父窗口 capture 裁决——单窗口集中制） |
| 交互 | `SetCapture` 全屏跟踪 hover；点窗外/失活/Esc 关闭；**模态中忽略再入右键**（防嵌套菜单） |

**踩坑（三个，全在真机层，mock 测不到）**：
1. `WS_EX_LAYERED`(**0x80000**) 必须带——**没有它 `UpdateLayeredWindow` 静默失败**，
   内容永不上屏（窗口全透明，正是"字体重叠"的现场）；且首次修复时我误用
   `0x08000000`（那是 WS_EX_NOACTIVATE 的位），值必须精确。
2. `WNDCLASSW.lpfnWndProc` 是 `c_void_p`：WINFUNCTYPE 需 `ctypes.cast(..., c_void_p)` +
   **模块级持有回调**防 GC（`_MENU_WNDPROC_STUB`）。
3. `_render_item` 的 sep 分支调 `round_rect` 少传 `r` → 首次真机弹菜单时崩；离屏驱动
   `_render()` 全条目（含 sep）能提前抓到这类问题。

**为什么不用系统菜单**：`TrackPopupMenu` 的前两轮修复（`MF_OWNERDRAW=0x100`、
`WM_MEASUREITEM=0x2C`/`WM_DRAWITEM=0x2B`、去 `TPM_NONOTIFY`）已让 owner-draw 能用，
但背景合成这个根本限制在系统窗口里无解 → 自绘是唯一出路。相关 SDK 真值常量与
owner-draw 协议代码**保留为档案**（[G8] 断言防手抄错；`tools/_repro_menu.py` 留作
协议最小复现工具）。

**验证**：本地进程 E2E（真弹真截：白卡/圆点/分隔线/危险红全对）+ 桌宠进程 5 项实测
全过——菜单弹出 / hover 子菜单展开（截图含真实时间线数据）/ Esc 全关 / 点击「音效」
分发成功且菜单自关 / 再点恢复。`test_menu_toggles.py` **28 项 PASS**（新增 [H] 数据层 6 项，
