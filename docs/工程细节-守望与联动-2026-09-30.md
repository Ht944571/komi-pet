## 1. 三个常驻进程

| 进程 | 脚本 | 职责 |
|---|---|---|
| **桌宠本体** | `app/hover.py` | 窗口 + 动画 + 气泡 + 右键菜单。改代码/素材后要重启的就是它 |
| **守望** | `app/wb_whale_watcher.py` | 保活桌宠（崩溃/被杀 → 拉起）· 联动关闭兜底（agent 全退 → 灭杀遗留桌宠）· 登录自启注册 |
| **看板 API** | `app/wb_usage/wb_api.py --port 8801` | 看板页面 + 接口 + **采集器**（它在自己进程里 import 数据源；改源必须重启它） |

关系：**桌宠的 `api_guard` 守着 API**（60s 探一次、60s 冷却）→ 于是"API 挂了"能自愈；
**守望守着桌宠**；2026-09-30 又给 **API 加了兜底：桌宠窗口 + 守望都不在 → 拉起守望**
（`wb_api._ensure_watcher`，10 分钟一次冷却）。三者互锁，任一个死掉还有另外两个兜。

**重启/自检**（用户侧）：
```
双击 D:\workbuddy\古见同学桌宠\start-pet.cmd      # 守望 + 桌宠（+ 桌宠再把 API 拉起来）
双击 D:\workbuddy\古见同学桌宠\start-dashboard.cmd # 只起看板 API（前台控制台）
python app\wb_whale_watcher.py --status            # 自检：活跃 agent + 桌宠在不在
```
⚠️ `start-pet.cmd` 这类 `.cmd` **必须纯 ASCII**（cmd.exe 按 OEM 码页解析，中文/em dash 会把行拆了报怪错）。
⚠️ 转帧需要停桌宠时：**同时停守望**（否则它会把桌宠拉回来锁住 PNG）→ 转完 → 让用户双击那个 cmd。

## 2. 联动关闭（「随 Agent 退出联动关闭」）的真实语义

**不是"跟着 WorkBuddy 走"，而是"跟着任一已注册 agent 走"**（2026-09-25 v2 解耦）：

- 判据链：桌宠 `_check_linked_close(now)` → `_wb_alive(now)` → `_host_alive()` →
  `self._presence.active()`（桌宠内跑着的活跃探测器缓存，零额外开销）。
- **活跃 = 任一 enabled agent 命中 L1/L2/L3 任一层**（见 §3）。所以：
  **关掉 WorkBuddy 但 opencode/zcode 还开着 → 桌宠不退出**（这是设计，不是 bug）。
- 触发要求：连续 `LINKED_CLOSE_CONFIRM_CHECKS=3` 次判定"已消失" **且**持续
  `LINKED_CLOSE_GRACE_S=30s`（**2026-09-30 从 3s/2 次放宽**：真实的"agent 全退"会持续几分钟，
  而宿主重启/一次进程快照失败只有几秒 —— 3 秒就关会把桌宠误杀）。
- 基线：`_linked_expected`（守望拉起，注入 `WB_PET_LINKED=1`）**或**曾见过宿主存活，
  二者之一满足才允许联动关；手动直接跑、从没见过宿主（如测试）→ 永不自动关。
- 落地：`_linked_quit()` → `WM_CLOSE` → `WM_DESTROY` → `PostQuitMessage`。
- **留痕**（2026-09-30 加）：判定"看不见宿主"时报 `host_gone`（哪怕随后恢复也留证据）；
  WM_CLOSE 时报 `close_req`；真退出时报 `linked_close`（带时长 + 次数）。
  → 从此"桌宠无声消失"能在 `%TEMP%/komi-wb-hover.events.log` 里分清是**被杀**还是**自己退**。

## 3. 活跃探测（`wb_agent_presence.py`）：三级降级

| 层 | 信号 | 窗口 | 语义 |
|---|---|---|---|
| L1 | hook 心跳文件 mtime | 90s | "本轮活跃"（最可信） |
| L2 | 会话日志最近写入时间 | 45s | "忙碌"（不需 agent 配合；CLI 类主要靠它） |
| L3 | 进程名 / 端口在听 | — | "在跑"（唯一持久信号） |

探针是**声明式**的（`assets/_agents.json` 的 `presence.procs/ports` + `caps`），新增 agent 只改 JSON。
每个 agent 取**最强可用**的一层；**不在返回里 = 本轮不活跃**。

🔴 **三值语义是命门**：`_running_procs()` 的 `CreateToolhelp32Snapshot` 在进程高频起停时会失败，
**失败必须返回 `None`（探测未知），绝不能当成"没有进程"** ——
否则一次快照失败 = "所有 agent 都不在" = 守望把桌宠灭杀（2026-09-30 实锤的根因）。
配套：
- `detect_detail()` 快照失败 → **跳过 L3**（L1/L2 照常）；
- `detect_once()` 快照失败 → 返回 **None**（守望据此"本轮不判"）；
- `PresenceDetector.poll_now()` 快照失败 → **保留上一次活跃集合**（桌宠的宿主判据不闪空）。

## 4. 守望侧的灭杀：纯判定 + 去抖

- `should_kill_on_session_end(prev, cur)`（纯函数，可单测）：`prev` 非空 **且** `cur` 是**空集**
  （不是 None）→ True。`None`（探测未知）永不触发。
- **`KillDebounce`**（2026-09-30 加）：连续 `KILL_CONFIRM_ROUNDS=6` 轮（5s/轮）
  **且**跨度 ≥ `KILL_CONFIRM_S=25s` 都判"该杀"才真杀；期间 agent 回来了 → 计时取消。
  单轮就下手 = 一次瞬时误判就杀掉桌宠，而桌宠不会自己回来。
- `kill_whale()`：`WM_CLOSE` 礼请 → 2s 未退 → `TerminateProcess`。
  ⚠️ 桌宠忙（长 tick）时来不及处理 WM_CLOSE 就会被强杀 —— 强杀**不留任何日志**，
  这正是"无声消失"的历史特征。
- **单实例互斥体** `KomiPetWhaleWatcher.SingleInstance`：`main()` 常驻模式先
  `CreateMutexW`，`ERROR_ALREADY_EXISTS` → 本实例退出（**永不出现双守望**互相拉扯）。
  API 的兜底拉起也用 `OpenMutexW` 判断"守望还在不在"。
- **守望日志**：`%TEMP%/komi-watcher.log`（启动、每轮集合变化、灭杀计时/取消、灭杀、拉起、异常；
  512KB 轮转）。pythonw 没控制台，出事只能靠它。
  ⚠️ `KillDebounce._log()` 写的就是这个文件 → **测试里实例化它必须先静音 `WATCH._log`**
  （否则测试输出会被当成"守望 churn"，2026-09-30 白追一轮）。

## 5. 事故档案：桌宠一天无声消失 4 次（2026-09-30）

- **现象**：07:37 / 15:17 / 16:50 / 17:06 各消失一次（把事件日志按 ">4 分钟无行为事件" 切片即可看出），
  没有 `linked_close`、没有崩溃日志、守望也一起没了。
- **根因**：守望**单轮**判空就灭杀 × 探测会**瞬时闪空**（快照失败被当成"没进程"）。
  两层叠加：一次误判 → `kill_whale()` → 桌宠被强杀（不留痕）→ 守望若同时不在，就再也没人拉起。
- **修法**：§2 的宽限放宽 + §3 的三值语义 + §4 的去抖与互斥体 + §4 的 API 兜底 + 全链路留痕。
- **验证**：`test_linked_close.py` 40 项（含 D 去抖 / E 兜底判定 / F 互斥体）；真机把三件套跑起来后
  `_pet_fps.py` 采样 24.8 帧/秒、最长无变化 0.06s；守望日志里只有
  `守望启动 → 拉起桌宠 → 桌宠在了`，**零灭杀**。
- **怎么查下一次**：`%TEMP%/komi-watcher.log`（守望判了什么、做了什么）→
  `%TEMP%/komi-wb-hover.events.log`（`host_gone` / `close_req` / `linked_close`）→
  `%TEMP%/komi-wb-hover.err.log`（Python 异常）。三者都没有 = 进程被外部强杀（任务管理器/沙箱清理）。
