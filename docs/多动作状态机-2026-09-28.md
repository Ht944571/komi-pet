# 桌宠多动作状态机 + 音效（2026-09-28）

> 上一版：[`形态收敛-2026-09-28.md`](形态收敛-2026-09-28.md)（那天把桌宠收敛成「只会写字」）
> 这一版把**待机行为**补回来了：坐着、犯困、打瞌睡、醒来、拿本子 —— 五段素材，
> 加上写字一共 7 个动作，由状态机串成一条完整的生活流。

---

## 一、动作与状态流转

```
idle(坐着循环) ──空闲 3 分钟──► doze(变困) ──► sleepy(困了循环)
     ▲                                              │
     │                                       来任务  │
     └──────────────── wake(醒来) ◄─────────────────┘
                          │
                          └─► pickup(拿本子) ──► write(写字循环)
                                                       │
                              idle ◄── present(举本子展示) ◄── 任务完成
```

| 动作 | 素材 | 播法 | 什么时候 |
|---|---|---|---|
| `idle` | `anim/idle/` 54 帧 | **循环** | 常态（没有任务在跑） |
| `doze` | `anim/doze/` 54 帧 | 一次性 | 空闲超过 `MOTION.IDLE_DOZE_AFTER_S`（默认 180s） |
| `sleepy` | `anim/sleepy/` 54 帧 | **循环** | 变困播完 |
| `wake` | **复用 `doze`，倒放** | 一次性 | 睡着时来任务 |
| `pickup` | `anim/pickup/` 54 帧 | 一次性 | 坐着/醒来 + 来任务 |
| `write` | `anim/write/` 49 帧 | **循环写字段** | 任务进行中 |
| `present` | 复用 `write` 的后段 | 一次性 | 任务完成 → 翻页 + 举本子 |

**`wake` 不单独做素材** —— 把 `doze` 倒放就是「从托腮变回端坐」，
观感正好是醒过来，而且首尾帧天然与 `sleepy` / `idle` 对齐。省一半素材还更准。

**触发判据与气泡 OK 态同源**：`_sync_bubble_mode` 里的「运行中会话数」。
两者是不同变量但同一个 n —— 改任一边都要想到另一边，否则会出现
「气泡说完成了、她还在写」这种自相矛盾的画面。

## 二、声音

**五段素材里有四段自带音轨**（坐着 / 困了 / 拿本子 / **写字**），**变困那段是静音轨**。

| 动作 | 音效 | 播法 |
|---|---|---|
| 坐着 / 困了 / 写字 | 有（各 ~190KB） | **`SND_LOOP` 循环**（都是持续状态，播一遍就没声了） |
| 拿本子 | 有 | 播一遍 |
| 展示 | 复用写字的音效 | 播一遍 |
| 变困 | **没有** | 不硬塞（素材本身静音，`_play_anim_sfx` 会记住状态、不每帧重试） |

- **统一峰值到 60% 满量程**。原始峰值差了 5.7 倍：`pickup` 95%（会刺耳）、
  `idle` 16.7%（几乎听不见）—— 不归一化三个状态响度完全不成比例。
  每段约 180~190KB，放 `assets/anim/<动作>/_sfx.wav`。
- **素材与循环动画几乎等长**（4.14~4.48s vs 4.5s）→ 循环时音画基本同步。
- **右键菜单「音效」**：这是**总开关**（互动音效 + 动作音效都归它管）。
  关掉立刻 `SND_PURGE` 静音，打开立刻把当前动作的音效接回来。
- ⚠️ **winsound 一次只能播一个**：点击的互动音效（pop/chirp…）会打断动作音效，
  所以 `_play()` 里记了个 `_sfx_resume_at = now + 0.6`，0.6s 后自动把动作音效接回来 ——
  否则「点一下之后就永远静音了」。

> 两个踩过的坑（2026-09-28）：
> ① **写字那段也有音轨，第一版漏了** —— 我当时只处理了用户新给的 4 段。
> ② **菜单文案没跟着改**（文档写了「互动音效」→「音效」，代码没动）。
> **改了文档要回头核对代码**，不然「文档说改了、代码没改」比不写文档更坑。

## 三、两套素材的构图差异 → 已用 `HEAD_SCALE` 对齐

两批素材的**取景距离不一样**：

| | 写字（write） | 四个待机动作 |
|---|---|---|
| 画面内容 | **全身**坐姿（抱着本子） | **近景**（头占画面很大） |
| 内容框 `y0` | 0.357 | 0.494 ~ 0.526 |
| **头高 / 画布** | **43%** | **34%** |

直接播的话，切到写字的瞬间她的头会明显变一下。

**解决**：`wb_anim.HEAD_SCALE` —— 待机四段 **×1.27**，写字 **×1.0**，
在 `_draw_anim_frame`（`ph_draw` 乘倍数）与 `_build_draw_cache`（预缩放尺寸同步）两处生效。

### 1.27 是怎么定出来的（过程比结果值钱）

自动测量**试了四种全失败**：

1. **宽度剖面找脖子** → 被头发中分的凹陷骗了（量出 40px）
2. **颜色找脸** → 脸被刘海/腮红切成碎片（量出 38×12）
3. **脸的行投影找下巴** → 写字那张**抱着本子**，把本子当成了脸
4. **眼睛白色高光点** → 检到的点不是同一个特征，四个待机动作结果互相矛盾

**最终有效的办法**：把五段首帧（×1.0）各裁「**头顶往下 45% 画布**」并排比对，
**肉眼**读下巴位置 → 待机 **34%** vs 写字 **43%** → 放大 **1.27**。

> 🔴 **最大的坑**：一开始用 **30% 条带**读，**把写字的「脖子/衣领」当成了下巴**，
> 于是得出「待机头更大」的**反向结论**，白调了一轮（先缩到 0.80、又缩到 0.72）。
> **读下巴要留足够的条带高度，别让条带把下巴切在外面。**
>
> 另一个教训：在这套素材上**自动测头大小不可靠**（道具、刘海、表情都会干扰），
> **并排条带 + 肉眼**反而是最稳的 —— 不该在自动测量上耗那么多轮。

### 效果与边界

- ✅ **头大小一致**：五个动作的头顶、眼睛、腮红位置现在对得上。
- ⚠️ **整体大小仍有差**：待机是近景素材，放大后她占屏更满（内容高 0.474×1.27 ≈ 0.60
  vs 写字 0.643，已经很接近了）。**头身比本来就不同**，只能做到「切换时头不跳」，
  做不到「看完全是同一个人」。

守护这条的断言（`test_anim.py`）：写字 = 1.0 / 四个待机倍数一致 / 待机是放大 / 放大后不横向溢出。

## 四、代码改动

| 文件 | 改了什么 |
|---|---|
| `wb_anim.py` | `WritingPhase` → **`PetPhase`**（多动作状态机）；新增 `ACT_*` 常量、`CLIP_OF`（wake→doze / present→write）、`load_all()`；`AnimClip.index(act, t0, now)` 按动作决定循环/一次性/倒放 |
| `wb_whale_win.py` | `_anim_clip` → **`_clips` / `_anim_caches` / `_anim_imgs`**（按动作分桶，否则不同动作的同号帧会串）；`_spr_cbox["__anim__"]` 改成**每帧按当前动作刷新**（各动作近景程度不同，锚点必须跟着走）；新增 `_load_anim_sfx` / `_play_anim_sfx` / `_stop_anim_sfx`；菜单「互动音效」→「音效」 |
| `wb_motion.py` | 新增 `IDLE_DOZE_AFTER_S = 180.0` |
| `tools/test_anim.py` | 重写：新增**状态机流转**断言（idle→pickup→write→present→idle、idle→doze→sleepy→wake→pickup）与 wake 倒放断言 |

**回归**：13 个测试文件全 PASS · `_check_refs.py` 干净 · `verify_win.py` 打包实测 17/17。

**帧率与内存**（2026-09-28 晚按用户要求「流畅优先、帧数不要减少」调整过）：

| | 值 |
|---|---|
| 每段帧数 | idle/doze/sleepy/pickup 各 **107 帧**，write **97 帧** —— **按源片 24fps 一帧未减**（共 525 帧） |
| 素材体积 | `assets/` 约 **50MB**（原 12fps 时 26MB） |
| 打包 zip | **76.4MB**（原 51.6MB） |
| 桌宠内存 | **~132MB** |

**内存能压住的关键**：`_build_draw_cache` 建完**预缩放缓存后立刻释放原始位图**
（`_anim_imgs`）。
原始位图每帧约 950KB、预缩放后每帧约 350KB —— 525 帧下差 **约 300MB**。
不做这步，24fps 直接会顶到 500MB+；做了之后 132MB **比 12fps 时还小**。
（窗口尺寸变化时会走回 `_anim_image` 重新加载，所以释放不影响 resize。）

## 五、踩的坑

### 5.1 `_check_refs.py` 抓不到「属性链」上的错

我把 `WritingPhase.phase` 改成了 `PetPhase.act`，但 `wb_whale_win.py` 里还有
`self._wr.phase` 的读取 —— **静态自检没报**，因为那个脚本只检查
`self.xxx()` 的**方法调用**，不检查 `self.a.b` 这种**属性链**。

结果：6 个测试一起挂（都走到 `_sync_bubble_mode` 就炸）。
→ **改字段名时，要额外 grep 一次旧字段名**，别只信自检脚本。

### 5.2 日志里那条「缺写字帧序列素材」是虚惊

启动瞬间会先有一次 `draw()`（在 `_build_draw_cache()` 之前或之中），
那一帧缓存还没建全 → `_draw_anim_frame` 返回 False → 打印一次告警（只报一次）。

**怎么区分「虚惊」和「真画不出来」**：写了 `_verify_multi.py` 直接看返回值，
七个动作全 `画出=True`。→ **帧序列方案要有个能问「到底画出没有」的探针**，
不能只看日志有没有告警。

### 5.3 `os._exit(0)` 会把输出吞掉

验证脚本最后用 `os._exit(0)` 跳过 GDI+ 清理，结果**连 print 的内容都没了**
（跳过 stdout 刷新）。→ 先 `sys.stdout.flush()` 再退，或者用 `python -u`。

### 5.4 🔴 重转素材前**必须先停桌宠**，而且不能只看日志判断成败

24fps 重转那次踩了两个连环坑：

1. **`os.remove` 旧帧被 safe-delete 拦下（中文路径）→ 抛异常 → 整段转帧中断**。
   最阴的是：前面的「帧画布 / 抽到 107 帧 / 统一内容框」日志**全都正常打印**，
   只有最后那行 `✅ 107 帧 → 目录` 不出现 —— **看起来像转好了**。
   → 修了脚本（删除包 try/except），但**光修这个还不够**：
2. **覆盖写被拒**：`PermissionError: [Errno 13] Permission denied` ——
   桌宠通过 GDI+ **持有这些 PNG 的句柄**，文件根本写不进去。
   → **转帧前先 `taskkill /PID <桌宠>`**。（守望不用停，它没来得及把桌宠拉回来；
   但转帧要是更慢，就把守望一起停 —— 停守望得带 `/F`。）

**教训**：**转帧（或任何改素材）之后，直接读 `_anim_meta.json` 核对 `count` / `fps`，
不要拿日志有没有报错当成功判据。** 那次白跑了 6 分钟才发现「其实一帧没转」。
